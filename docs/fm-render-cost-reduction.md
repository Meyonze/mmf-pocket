# 実験用FM合成の処理量を減らす

[明示的に選ぶ再生経路](fm-player-sine-render.md)の追加サンプル計算とFIRを軽量化しました。
通常の`tick()`、公開アプリの既定設定、正式版1.6.6、変換キャッシュr82は変えません。

## 厳密なゼロ音量

追加サンプル生成では、ベロシティまたはチャンネル音量が厳密に0のときだけ、途中の波形計算を省きます。
先に元の`tick()`を1回呼ぶので、位相・EG・LFO・Hold・解放・発音枠評価は進みます。
最後のサンプルは元の出力をそのまま保持し、音量を戻した直後や再発音時も元の時刻へ復帰します。
小さい音を省くしきい値はありません。

エンベロープのゼロ判定や未使用の変調器を省く案も比較しましたが、共有ホストの通常発音で
処理量が増える傾向があったため採用していません。採用した音量判定は、通常発音と小さい音の
32条件を複数回測り、中央値の比は約0.99でした。小さな差は測定のばらつきとして扱います。

32声・32倍・並列4演算器・Hermiteの、音量0の1,024フレームでは、共有ホストの中央値は
約49.5msから約6.2msになりました。合成部分だけの測定で、端末の速度や消費電力の値ではありません。

## 左右のFIRをまとめる

左右で同じ係数・時刻を使う処理を、ステレオのリング履歴へまとめました。
係数と添字の読み出しを共通にし、左右の計算をコンパイラーが並列に処理しやすくしています。
各チャンネルの加算順序・係数・間引き位相・共通遅延・有限の末尾は保ちます。
プレイヤー間の可変履歴は引き続き独立しています。

共有ホストの連続入力44,100フレーム、各3回の中央値は、8倍で約9.68msから約6.54ms、
32倍で約32.98msから約19.26msでした。合成・ミックス・ファイル入出力は除いたバス単体です。
全45条件で、フレーム処理中の通常のC++ `new`は0回でした。Androidの数値測定は未実施です。

## 検証と再実行

- 通常のFM約315万サンプルは、変更前とビット単位で一致。
- 960条件・約229万追加サンプルを変更前と照合。値と全状態を保持し、追加サンプルのゼロの符号だけは比較時に正規化します。元の終点はゼロも含めてビット単位で比較します。
- 低速ARの追加ビット、小さい音量、音量の復帰、Nyquist超えと復帰、Hold・解放・再発音を含みます。
- 実際のプレイヤーの混在・停止・曲末と、独立した密なFIR基準との検証を維持。
- 通常WAV2,121件と、実験用の24条件のWAV全体が、変更前とバイト単位で一致。

```sh
mkdir -p build/fm-subframe-zero
c++ -std=c++20 -O2 -Ithird_party/yamaha-smaf-player/src tools/fm-subframe-zero-test.cpp build/native-render/libsmaf.a -o build/fm-subframe-zero/test
build/fm-subframe-zero/test
c++ -std=c++20 -O2 -Ithird_party/yamaha-smaf-player/src tools/fm-subframe-zero-cost.cpp build/native-render/libsmaf.a -o build/fm-subframe-zero/cost
build/fm-subframe-zero/cost > build/fm-subframe-zero/cost.json
```

測定ツールの`mode`は0通常、1音量0、2変調器のAR0、3キャリアのAR0、4並列の片側だけAR0、
5音量1e-12です。2〜4は採用しなかった案の比較にも使った対照条件です。
EOFを早めたり、低音量のパートを切ったりする変更ではありません。
