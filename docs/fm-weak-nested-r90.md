# r90：弱いVM35直列FMの折り返し低減

通常再生・プログレッシブ変換・WAV保存で、次の接続6にも16倍の追加サンプル生成と
既存のFIRを使います。接続は`op0 + (op1 → op2 → op3)`、元の混合係数0.5を保ちます。

- 4演算器すべてが正弦波で、実効フィードバックがない。
- 全演算器がVM35の周波数倍率で、MA7や互換形式との混在ではない。
- 動く変調器op1・op2のTLが両方24以上で、op1・op2・キャリアop3のアタック速度が非ゼロ。

TL24は既存の0.75dB刻みで約18dBの減衰です。二つの変調段を検証した範囲へ絞るための
適用条件であり、チップ仕様の境界を意味しません。これより強い変調や別の形式は追加対象に
していません。r89で既に扱う、無音の枝で2演算器へ簡約できる接続6は従来の判定を維持します。

この三演算器の変調には、既存の単一PM対の密度推定を使いません。アプリ方針では音程に
かかわらず16倍で開始し、発音中は固定します。TL・形式・設定されたアタック速度で対象を決めるため、
音量や余韻の変化で経路が切り替わることはありません。明示倍率のAPI/CLIでは2/4/8/16/32倍を比較できます。

元のnative tickと終点、位相・EG・LFO・recentLevel・発音枠の規則は保ちます。
8倍・16倍・その他の音源を既存の72フレーム遅延で揃えてから、共通LP・リミッター・
携帯風処理へ渡します。音量の正規化は加えません。変換キャッシュはr90、正式版は1.6.6のままです。

## 定常音と動的な波形

[ホスト試作](fm-nested-sine-prototype.md)の独立した二重Bessel基準を拡張しました。
音程48/72/84/96/108/120、三組の周波数倍率、変調器TL24/36/63の四組、計75素材について、
2/4/8/16/32倍のExact/Hermite、750設定を比較しています。有限FIRと出力LPまで含む
最大RMS誤差は約1.54e-8です。音程124/125/127・倍率2/2/2の三条件も加え、native Nyquist境界の前後を確認しています。通常方針の出力は、独立して指定した固定16倍と全サンプル一致しました。

音程96、内側倍率7・中間3・キャリア5、変調器TL24/24の例では、理想帯域とのRMS誤差が
従来約0.09048から16倍で約0.00000732へ低下しました。この値は自作の定常音色による例です。

さらに、ゲート1/17/441フレーム、強制停止/通常NoteOff、8/16/32倍のExact/Hermite、
36条件を独立した閉形式の波形と密なFIR畳み込みで比較しました。途中で2半音上げて戻す
音程変更と、ソフトウェアのRR15の減衰・終了を別計算に含めます。最大RMS誤差は約5.74e-9、
ピーク差は約2.42e-8でした。参照のEG・音色パラメーターは実行中の演算器から読み戻しません。

240条件の時計・Hold・再発音、4条件の発音終了、15条件の拒否を維持し、対象VM35の
公開sourceと試作の途中サンプルもビット比較しています。TLの9条件、対象外7条件、
従来の簡約接続6が8倍を維持する対照も検査します。

## 実ファイルと混在

82の実ファイルでは対象75素材のWAVが明示16倍と完全一致し、対象外7素材はr89と完全一致しました。
追加した素材を含む2,262入力の比較では、source状態・発音枠カウンターが全件一致し、
音声が変わったのは対象75素材だけでした。既存2,180入力の音声は維持し、二件は時間上限までの比較です。
既定のネイティブ経路では従来2,121素材のWAVも完全一致しています。

実WAV/JNIの検査は29構成へ拡張し、携帯風の有無、シーク、EOF、小音量、保存失敗を検査します。
PCM・独立ATRと混在するパート寄与の検査は、固定倍率56条件・自動方針56条件へ拡張しています。
GCC Release、ASan/UBSan、NDK ClangのLinuxホスト向け実行と、Android全ABIのLint/Debug/Releaseを通過しました。
ホストの実行検査はAndroid実機での実行ではありません。

## 範囲と残ること

位置計算は2の累乗の正確な逆数を共有し、対応する接続0/3/4/5/6/7のHermite処理は演算器ごとの行へ並べ替えました。
通常とFMA有効のそれぞれで、変更前後の1,440条件・4,571,136floatと発音状態がバイナリ一致しました。
対象VM35の途中サンプルも試作とのビット比較を維持し、実ファイル82素材のWAVも並べ替え前と一致しました。

同じCPUに固定し順序を交互にした7組のホスト測定では、共有する位置計算の変更で接続6/7の
16倍合成CPU時間が約5〜8%減り、接続6の行への並べ替えでさらに約37%減りました。
後者の対照の接続7は前後比約1.001です。32音・8,192フレーム（約186msの音声）の
合成部分だけでは、接続6だけ並べ替えた段階で接続6が約160ms、対照の接続7が約186msでした。
FIR・ミックス・入出力を含むアプリ全体の時間ではなく、共有ホストのばらつきもあります。

接続6だけ並べ替えた版に対し、他の対応接続にも同じ配置を適用すると、別の7組の
交互順測定で接続0/3/4/5/7の8倍・16倍CPU時間は約9〜45%減りました。
接続6の中央値の前後比は0.984〜1.031です。いずれも合成部分だけのホスト測定です。

16倍により対象音の計算量は増えます。全曲・全端末の速度や消費電力を保証する測定は未実施です。
今回の基準はソフトウェアの波形・EG・倍率規則であり、旧端末や他アプリとの音色一致の測定ではありません。
既存の演算器ごとのnative Nyquistミュートも保ち、参照にも含めています。そこを越えた演算器から
帯域内へ戻る変調成分を回復する処理は、時刻・発音枠・曲末を含めた別の検討が必要です。

強い変調、MA7・互換形式の一般的な接続6、全演算器が動く接続3/4、フィードバックは引き続き追加対象外です。
有限FIRの遷移帯域の誤差や16倍で残る成分もあり、全条件で倍率と品質が単調に対応する保証はありません。
