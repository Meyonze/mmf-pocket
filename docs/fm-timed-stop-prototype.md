# 遅延中の停止と再発音を分ける試作

[チャンネル別履歴](fm-channel-prototype.md)に続く、ホスト専用のタイミング実験です。
`tools/fm-timed-stop-prototype.h`を追加しました。アプリの再生エンジン、公開版1.6.6、
変換キャッシュr82は変更しません。

## 今回試した停止方針

音源の入力フレームnで強制停止したとき、その停止を共通群遅延の72フレーム後に反映します。
停止前の入力の寄与だけを除き、停止時刻以降に再発音した音は残します。
これは明示的なハードカットの候補であり、メーカー実機の停止方式を確認したものではありません。
本体の既存AllSoundOffは共有フィルターの履歴を保つため、そのまま同じ動作ではありません。

| 処理境界 | 試作の動作 |
| --- | --- |
| 音源入力n | 呼び出し側が対象の声を停止し、強制停止のフラグを渡す |
| nからn+71 | それまでの再生履歴を保持。新しい入力も蓄積 |
| n+72 | 入力nより前の寄与を除去。入力n以降の新しい音は保持 |

同じ入力フレームで「停止→NoteOn」の順に処理された場合、新しい音を残します。
「NoteOn→停止」なら呼び出し側でその声も止め、対応する入力をゼロにします。
通常のNoteOffやHoldは音源側の解放処理を使い、強制停止フラグを立てません。
他チャンネルや独立したATRの音源を止める処理は含みません。

## 入力履歴から再構成

直近73フレームのFMサブサンプルとネイティブPCMを保持します。
停止の出力境界ではフィルターを初期化し、停止時刻以降の73フレームだけを通して
現在の状態と出力を再構成します。FMのEGや位相を巻き戻して再合成する処理ではありません。

停止フラグも固定長のリングで保持します。連続する停止命令で世代別のフィルターが
増え続けることはなく、各出力フレームでの再構成は最大1回・73入力フレームです。
フレーム処理中の動的確保はありません。入力の検証はサンプル・命令キュー・時刻を進める前に行います。

`pendingFrames()`は音声だけでなく、遅延中の停止命令も含む処理上限です。
この値だけで公開WAVの長さを決める設計にはしていません。
全体リセットは音声履歴と未反映の停止命令を両方消します。

## 検証

Release O2とASan/UBSanの専用テストが通っています。

- 2／4／8／16／32倍、停止なし・単発・連続・高密度の停止、4種類の処理区間。
  57,600出力を、停止時刻より前の項を除いた独立した密な畳み込みと照合。
- 停止なしの場合は、既存の`AlignedBus`と出力が完全一致。
- PCMの停止は正確にn+72で反映し、翌フレームの1e-100の再発音も保持。
- 実FMのHold中の停止、連続停止、同一フレームと直後のNoteOn、PCM混在を確認。
- EOF・命令だけが残る区間・シークでの命令取り消し、不正入力拒否で時刻が進まないことを確認。
- 再構成回数を停止の出力境界と照合し、保持する入力が73フレームから増えないことを確認。

## 負荷と残る課題

共有ホストで、1チャンネル・4,096フレームのバス部分を5回ずつ測りました。
FM合成、ファイル入出力、Androidの再生経路は含みません。短時間の測定なので変動があります。

| 倍率 | 停止なし | 256フレームごとに停止 | 毎フレーム停止 |
| --- | --- | --- | --- |
| 8 | 約0.97ms | 約1.29ms | 約89.8ms |
| 32 | 約2.80ms | 約4.48ms | 約258ms |

高密度の停止では繰り返しの再構成が重くなります。メモリーと1回の作業量が有限でも、
多数のチャンネルを同時処理できる根拠にはなりません。この方式をそのまま本体へは適用しません。
停止命令を捨てたり音量閾値で省略したりせず、部分的な履歴更新や別の畳み込み方式との比較が必要です。

採用する停止方針、音色ごとの適用条件と倍率、倍率変更、WAVの先頭・末尾と時刻表示、
4演算器・フィードバック・非正弦波、端末負荷も引き続き確認します。
