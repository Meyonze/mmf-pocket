# 複数音源を混ぜるFM帯域制限の試作

[遅延停止の試作](fm-timed-stop-prototype.md)を、スコアチャンネルごとのミックスと、
独立した録音音声の入力へ接続しました。ホスト専用の`tools/fm-render-bus-prototype.h`です。
アプリ、公開版1.6.6、変換キャッシュr82は変更しません。

## 入力の経路

```text
各スコアチャンネル（0〜127）
├─ 対象の直列2正弦波FM → サブフレームで合成・加算 → FIRと追加遅延
└─ 対象外のFM・PCM    → ネイティブレートで加算  → 72フレーム遅延
                                                   ↓
                           チャンネルごとの停止処理 → ステレオ加算
                                                   ↑
独立した録音音声の入力                → 72フレーム遅延
```

FMの発音枠ごとではなく、チャンネルごとにフィルター履歴を持ちます。
同じチャンネルに、細かく合成するFMとネイティブレートの音源が混在しても扱えます。
チャンネルの強制停止は、独立した入力へ伝わりません。ATRなどの経路を想定していますが、
本体のATRデコーダーやイベント列へ接続した実装ではありません。

入力はパン・音量の適用後のステレオ値です。この試作に楽器別の音量補正はありません。
最終のリミッター・携帯スピーカー風モード・PCM16出力も未接続です。
前回同様、強制停止の候補方針を使い、メーカー実機の停止方式を決定したものではありません。

## 係数の共有と休止

同じ倍率の各チャンネルは、カスケードFIRの計算用係数を不変オブジェクトとして共有します。
`TimedStopPrototype::prepareKernel()`が準備し、共有ハンドルを使います。
入力履歴、遅延、停止命令、EG・LFOは共有しません。違う倍率の係数の指定は拒否します。
最後の利用者が手放すまで係数を保持し、フレーム処理中の共有ハンドルのコピーは行いません。

停止命令の残数を保持し、処理継続の要否を毎フレーム固定時間で判定できます。
音声・停止命令がなくなったチャンネルは休止し、無音入力も省略します。
発音中の音源のEG・位相を止める指定ではありません。音源側は従来どおり更新します。
バッチ全体の入力を検証してから処理するため、後半の入力が不正でも、前半のチャンネルや
独立入力の再生時刻だけが進むことはありません。

## 検証

Release O2とASan/UBSanで次を確認しています。

- 2／4／8／16／32倍、0・16・127の3チャンネル、処理区間1／7／64／257フレーム。
  14,400出力を、停止前の項を除く密な畳み込みと、固定した前回の再構成方式の両方と照合。
- チャンネルごとに異なる停止密度、入力バッチの順序変更、全体シーク、EOF、命令だけが残る区間を確認。
- 停止対象の寄与がなくなった後、他チャンネルと独立した音声は単独の経路と完全一致。
- 長い休止からの1e-100の入力の復帰、共有係数のハンドルを手放した後の動作、倍率不一致の拒否を確認。
- 8kHz／44.1kHz、2／8／32倍の実FM音源で3,600出力を比較。
  同一チャンネルの複数の声、Hold、連続停止、同じ時刻のNoteOn、音程・音量変更、
  フィードバック・4演算器のネイティブ経路、再発音時の適用対象の切り替え、PCM混在を含む。
  公開`FmVoice::tick()`と照合し、元の状態更新速度も保持。
- 既存の遅延停止テストも再実行し、129,600出力と余韻・命令の残り時間を照合。

```sh
mkdir -p build/fm-render-bus-prototype
c++ -std=c++20 -O2 -Ithird_party/yamaha-smaf-player/src tools/fm-render-bus-prototype-test.cpp build/native-render/libsmaf.a -o build/fm-render-bus-prototype/test
build/fm-render-bus-prototype/test
```

## メモリーと負荷

`tools/fm-render-prototype-cost.cpp`は、開始時のヒープ要求量と初期化・破棄時間、
実FM合成・PCM・独立入力を含む2,048フレームの処理時間を出力します。
通常のC++ `new`を単一スレッドで計測し、スタック・アロケーターの管理領域・
通常のC++確保を通らない`malloc`・プロセスRSSは含みません。

```sh
c++ -std=c++20 -O2 -Ithird_party/yamaha-smaf-player/src tools/fm-render-prototype-cost.cpp build/native-render/libsmaf.a -o build/fm-render-bus-prototype/cost
build/fm-render-bus-prototype/cost > build/fm-render-bus-prototype/cost.json
```

32チャンネルで、各チャンネルが別々の係数を持つ場合と共有バンクを比較した結果です。

| 倍率 | 個別の係数：要求ヒープ | 共有バンク：要求ヒープ | 削減 |
| --- | --- | --- | --- |
| 8 | 1,211,648 bytes | 932,160 bytes | 279,488 bytes |
| 32 | 3,174,144 bytes | 2,029,632 bytes | 1,144,512 bytes |

1／8／32チャンネル、8／32倍、休止・通常・全チャンネルで毎フレーム停止と再発音の
54回の測定で、フレーム処理中の通常のC++ `new`は0回でした。
FMの診断用の終点再構成も含む、検証用の合成経路を測っています。

共有ホストでの3回の中央値では、8音・8倍の通常処理は約15.5ms、32音・32倍は約230msでした。
2,048フレームは44.1kHzで約46.4msに相当しますが、これはホスト上の合成試作の値であり、
Android端末の再生速度の測定ではありません。実行間のばらつきも大きく、多数の音を
高倍率で常時処理できる根拠にはなりません。

## 次の判断

音色・音程・変調量ごとの適用対象と固定倍率、発音数が多い場合の扱いを決める必要があります。
途中で経路や倍率を切り替えるなら、音色の変化や不連続も検証します。
停止方針の採否、本体イベント・ATR・共有エフェクトとの接続、WAVの先頭と末尾・時刻表示、
端末負荷も未確認です。この経路を全音色へ一律に適用しません。
