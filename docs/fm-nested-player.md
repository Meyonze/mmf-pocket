# 強い直列FMを実MMFの変換へ接続

試作していた16/32/64/128倍の直列FMを、音源コア・実プレイヤー・WAV変換CLIへ接続しました。
明示的な実験オプションで使います。通常のアプリ初期化、変換キャッシュr91、正式版1.6.6は維持しています。

## 経路と対象

新しい`FmVoice::tickNestedSubframes`は、4演算器が揃ったmodern VM35/MA7の接続6、
全正弦波・実効フィードバックなし・固定周波数と非ゼロDetuneなしを扱います。
強いTL0の変調も、明示した固定倍率で比較できます。未確認の自動方針は追加しません。

Hermite方式では変調されない演算器0/1に検証済みの漸化式を使い、残りは演算器ごとの行で
処理します。Exact方式は正弦計算で比較できます。元のtickを一回だけ進め、最後のサンプル、
EG・LFO・Hold・発音枠、既存のnative Nyquist抑制と0.5倍の混合を保ちます。
従来の`tickSineSubframes`の上限32倍と、拒否時に状態・出力を変えない契約も維持します。

プレイヤーは`SineRenderOptions`の末尾の`nestedSine`を有効にした場合だけ、新しい経路を使います。
対応倍率は16/32/64/128です。対象外のFM、PCM、録音Audio、ATRはnative波形を72フレーム遅延させます。
この固定実験は、通常再生の8/16倍自動方針とは別の経路です。

64/128倍のバスも既存の33/37/257タップを使い、群遅延72フレーム、有限支持144フレームに揃えます。
通常経路と実験経路は別のテンプレート実体を呼び、従来の毎フレーム32要素の作業領域を維持します。
実験を使わない再生で128要素を毎回クリアする処理は加えません。

## 実ファイルでの比較

```sh
smaf-render input.mmf output.wav 30 \
  --experimental-nested-sine \
  --experimental-sine-factor=128 \
  --experimental-sine-math=hermite

render-contribution-audit input.mmf 30 \
  --experimental-nested-sine \
  --experimental-sine-factor=128 \
  --experimental-sine-math=hermite
```

通常の変換で64/128を指定した場合や、実験フラグだけ・8倍との組み合わせ・重複指定は拒否します。
C++では`SineRenderOptions{128, FmSubframeMath::Hermite, false, true}`に相当します。

寄与の診断は新しい経路でも実レンダラーと照合します。実験レポートには`nested_sine: true`と
64/128倍の発音フレーム数を追加します。既存の通常レポートのキーと値は維持します。

## 検証

- 160条件のコア出力が独立したホスト試作と全サンプル一致。元の発音時計・終点を維持し、
  不正な倍率・形状・数式方式・ポインターの12条件も状態と出力を変えずに拒否しました。
- 実プレイヤーの40設定が独立したBessel/FIR/LPモデルと一致。最大RMS差は約1.70e-7でした。
- 8構成で曲末、1/17/441フレームのハード上限とフェード、ブロック幅、シーク、再初期化、
  不正な初期化の後の再生継続、音量復帰、AllSoundOff、PCM/ATR混在と寄与カウンターを検査しました。
- 64/128倍の実バスを密なインパルス畳み込み、微小入力での再開、native遅延、有限余韻、
  リセット、不正ブロック拒否と照合しました。
- 録音Audio・ATR・WT・対象外FMの16条件は、元の音声に72フレームの遅延を加えたものと完全一致しました。
- 自作MMFからの実WAVで4倍率のExact/Hermiteを比較し、PCM16差は最大1段階でした。
  実ファイルのEOF、オプション順序、寄与レポート、拒否時に出力を作らないことも確認しました。
- 通常アプリの2,344入力で、PCM・発音状態・カウンターの変更前後のレポートが一致しました。
  従来の二件は時間上限までの比較です。保存済みr91に対する実アプリWAV164素材のSHA256も一致しました。

GCC Release、ASan/UBSan、NDK ClangのLinuxホスト向けFMA実行、Android全ABIの
Lint/Debug/Releaseを確認しています。ホストJNI・音源検査はAndroid実機での実行ではありません。

## 次の適用前に残ること

固定の実験経路なので、強い音色や音程に対して選んだ倍率で折り返しが残る場合があります。
定常時の倍率計画を実プレイヤーへつなぐには、切り替え時の履歴と過渡・混在負荷の検証が必要です。
高倍率の端末上の速度・消費電力、実機チップや元の音色への一致は未測定です。
native Nyquistを超えた演算器から帯域内へ戻る成分の回復も別の検討です。
