# 高倍率の直列FM：軽量化と定常時の倍率選択

64/128倍のホスト試作を軽量化し、16〜128倍を選ぶ計画用のコードを追加しました。
通常再生への組み込み前の検証です。アプリの対応範囲・キャッシュr91・正式版1.6.6を維持しています。

## 正弦波の漸化式と演算器ごとの処理

接続6の演算器0/1は他の演算器から変調されません。nativeの1フレーム内では周波数が一定なので、
最初のsin/cosから回転の漸化式で途中サンプルを生成します。変調される演算器2/3は既存の
Hermite方式を使い、演算器の行を先に完成させて次の行へ渡します。

位相刻みの絶対値が0.2rad以下のとき、sinは9次、cosは10次のTaylor多項式を使います。
打ち切り誤差はそれぞれ`0.2^11/11!`、`0.2^12/12!`以下です。正確な回転の2ノルムは1なので、
係数誤差εの累積は最大127回で`(1+ε)^127 - 1`以下になります。浮動小数点の丸めも別途検査します。
刻みが大きい場合は従来の計算を使い、2/4/8倍は従来のホスト試作を呼びます。

約212万点の位相比較で、doubleの最大差は約6.66e-14でした。2〜128倍、通常/MA7/互換形式、
停止アタック、EVB、低位アタック、音程変更、ゼロ/微小音量、Hold、再発音の210条件で、
元の終点と発音時計・状態を一致で照合しました。途中サンプルの従来試作との差は最大約5.67e-7です。
フレーム処理でヒープを確保せず、読み出す行のセルはすべて先に書き込みます。

独立したBessel/FIR基準との56設定の最大RMS差は約4.54e-7でした。
短音・二半音の音程変更・強制停止・通常NoteOffの72条件では、密なFIR畳み込みとの
最大RMS差は約1.20e-7、ピーク差は約6.52e-7です。
GCC Release、ASan/UBSan、NDK ClangのLinuxホスト向けFMA実行で確認しています。
ホスト実行はAndroid実機での実行ではありません。

## 共通の周波数刻みを仮定しない上限

前の複素位相による上限は、既知の周波数格子を必要とします。演算器ごとのビブラート等に
備えるため、`fm-nested-tail-bound.h`へ格子に依存しない上限も追加しました。
以下は定常時の正弦波と、固定した変調指数についての式です。

Grafの恒等式と`I0(z) <= exp(z)`から、任意の正のdについて、

```text
Σ_k |J_k(x)| exp(a |k|)
  <= sqrt(2 coth(d)) exp(|x| sinh(a+d))
```

を得ます。これを直列部分のkとnに適用します。正のy、c、dに対して、周波数の絶対値が
T以上の係数の絶対値和を、次で抑えます。fはnativeサンプル当たりのcycles、βはradです。

```text
2 sqrt(coth(c) coth(d))
  * exp(fC y + β2 sinh(fM y + β1 sinh(fI y+d) + c) - T y)
```

Tは`内部倍率 - 0.5`です。複数の正のy/c/dを調べ、小さい有効な上限を使います。
これは三角不等式で`|fC+n fM+k fI|`を扱うため、周波数の共通格子や相対位相に依存しません。
数値実装の入力域は、変調指数0〜32、各周波数0〜0.5cycles、Tは正の128以下に限定します。
20条件の重み付きBesselエネルギー、45条件のCauchy上限、共通格子を使わない二つの周波数組の
8条件の係数尾部と照合しました。

## 必要倍率を選ぶホスト試作

`fm-nested-density-plan.h`は、呼び出し側の尾部予算・倍率上限に収まる最初の
16/32/64/128倍を返します。どの倍率でも上限を確認できなければ、未確認を示す0を返します。
0は無音化やnative経路への切り替えを指示する値ではありません。
既知の周波数格子を使う従来の上限も明示して選べます。

原波形の係数尾部予算を1e-4とした自作VM35の例です。TLは二つの変調器に共通です。

| 音程・内側/中間/キャリア倍率・TL | 選択倍率 |
| --- | ---: |
| 84・3/2/5・18 | 16 |
| 96・7/3/5・18 | 64 |
| 84・3/2/5・12 | 32 |
| 96・7/3/5・12 | 128 |
| 84・1/1/1・0 | 32 |
| 96・3/2/5・0 | 未確認 |

独立した二重Bessel係数の尾部、呼び出し側の倍率制限、より厳しい予算の選択も検査します。
保守的な上限なので、数値実験で十分に見える倍率より高い倍率を選ぶ場合があります。

## 負荷と残ること

同一CPUに固定し、順番を交互にした7組の測定では、従来のスカラー試作に対するCPU時間の
中央値の比率は、64倍で約0.54〜0.60、128倍で約0.51〜0.61でした。
共有ホストの変動があり、既存アプリの演算器ごとの処理に対する改善率ではありません。

| 同時発音 | 倍率 | 従来試作 | 軽量化試作 |
| --- | ---: | ---: | ---: |
| 1 | 64 | 20.0ms | 11.7ms |
| 1 | 128 | 38.3ms | 23.0ms |
| 8 | 64 | 140.7ms | 77.7ms |
| 8 | 128 | 266.3ms | 139.1ms |
| 32 | 64 | 547.2ms | 298.5ms |
| 32 | 128 | 1,065.3ms | 543.8ms |

4,096フレーム（約92.9msの音声）の、試作ソース・ミックス・共有ステレオFIRだけのCPU時間です。
LP、リミッター、JNI、入出力は含まず、端末上の速度や電力を表すものではありません。

この上限と選択は定常音の係数尾部に関するものです。有限FIRの遷移帯域、EG・コントローラーの
過渡、曲全体の混在出力の誤差を保証しません。実プレイヤーへ組み込む前に、倍率を切り替える
際の履歴・余韻、音源終了、寄与カウンター、負荷を検証する必要があります。

```sh
./fm-high-density-cost 64 8
./fm-high-density-cost 64 8 --recursive
```
